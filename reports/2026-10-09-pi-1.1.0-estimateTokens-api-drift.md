# pi 1.1.0 API drift — `estimateTokens` left `pi-agent-core` — 2026-10-09

## Objective and scope

Explain and fix a hard failure that killed **every** turn of the installed pi, including a
plain greeting, with no tool involved:

```
Error: (0 , _piAgentCore.estimateTokens) is not a function
If this looks like a pi bug, /bug sends a report to the developers.
```

Only four extension files were edited. No provider, model, credential, skill or user
configuration was changed; `~/.pi/agent/settings.json` and the running pi install were left
untouched. No Git commit, push or deployment was performed.

## Symptom and evidence

The failing session record
(`~/.pi/agent/sessions/<workspace>/<session>.jsonl`) pins the exact
moment of failure. Every assistant message — tool-calling and plain text alike — is written
with:

```json
"stopReason": "error",
"errorMessage": "(0 , _piAgentCore.estimateTokens) is not a function"
```

The thinking block and the emitted tool calls are present; no `toolResult` message ever
follows. The throw therefore happens **after the model replies and before the tool runs**,
in the per-response path. A plain "你好" reply failing identically rules out tools, skills
and capability loading as the trigger.

## Root cause

`_piAgentCore` is the compile-time mangling of the external specifier
`@earendil-works/pi-agent-core`. That form is produced **only for extension code**: pi's own
compiled core imports its helpers with relative specifiers, which never yield
`_pi<Package>`. So an extension in the loaded suite is the caller.

The installed pi is **1.1.0** (matches `lastChangelogVersion" : "1.1.0"` in settings) at
`~/.nvm/versions/node/v24.13.1/lib/node_modules/@earendil-works/pi-coding-agent`. Its
`pi-agent-core` 1.1.0 exports exactly eight runtime keys:

```
Agent, agentLoop, agentLoopContinue, runAgentLoop, runAgentLoopContinue,
runToolCall, setDefaultStreamFn, streamProxy
```

`estimateTokens` and `calculateContextTokens` are **gone from that package**; the whole
compaction subsystem moved to `@earendil-works/pi-coding-agent`
(`dist/core/compaction/index.js`, re-exported from the package index).

Why it fails at runtime while `tsc` stays green: pi unifies the module instance an extension
sees with the host's own. `core/loader.ts` `getAliases()` rewrites the specifier
in normal Node runtime, and `virtual-modules.ts` `VIRTUAL_MODULES` maps it to the core
bundled into the binary in compiled/bundled runtime. Either way the extension is bound to
the **installed pi's** copy — never its own `node_modules`. The repo's pinned `0.87.1` types
(where `estimateTokens` was still exported by `pi-agent-core`) only guaranteed compilation.

Version boundaries measured on disk:

| pi-agent-core | `estimateTokens` at package entry |
| --- | --- |
| 0.74.0 | absent |
| 0.75.4 – 0.87.1 | present |
| 1.1.0 | absent — moved to `pi-coding-agent` |

The 0.87.1 → 1.1.0 jump is the dangerous direction: extensions compile cleanly against the
pinned types and explode only at runtime.

## Changes

`provider-manager/lib/message-utils.ts` — this is the hot path.
`applyCustomProviderContextUsage()` runs on every response finalization
(`tolerant-stream.ts:599`, `anthropic-stream.ts:539`, plus the `stream-compat` copies) and
calls `estimateLocalPayloadTokens()` **unconditionally**, which called the missing symbol.
Any session on a custom provider (`gptplus-openai` is the configured default) died here.

```diff
-import { calculateContextTokens, estimateTokens } from "@earendil-works/pi-agent-core";
+import { calculateContextTokens, estimateTokens } from "@earendil-works/pi-coding-agent";
```

`context-usage.ts` (`/context` breakdown):

```diff
-import { estimateTokens as estimatePiTokens } from "@earendil-works/pi-agent-core";
+import { estimateTokens as estimatePiTokens } from "@earendil-works/pi-coding-agent";
```

Test stubs kept in sync, so the harness does not keep validating a fictional core:

- `provider-manager/__tests__/pi-coding-agent-stub.ts` — gained `estimateTokens`
  and `calculateContextTokens`.
- `provider-manager/__tests__/pi-agent-core-stub.ts` — reduced to a comment; the
  stub loader aliases the specifier, so a stub still exporting the moved symbols would have
  hidden exactly this class of regression.

Deliberately **not** changed: `lib/agent-bus.ts:37` imports `type AgentMessage`
from `pi-agent-core`. It is a type-only import, erased at compile time, and cannot throw
`is not a function`. `parallel-agent` was untouched — it uses its own local
`estimateTokens` in `lib/helpers.ts`, not the core one.

## Verification

- `tsc --noEmit -p tsconfig.json` — clean.
- `temp/verify-fix.mjs` — `pi-coding-agent@1.1.0` yields both symbols as functions and they
  evaluate correctly on the extension's real payload shapes
  (`estimateTokens(user) = 5`, `estimateTokens(assistant with toolCall) = 8`,
  `calculateContextTokens = 175`); `pi-agent-core.estimateTokens === undefined`.
- `temp/audit-runtime-symbols.mjs` — walks every `**/*.ts`, skips `import type`
  and per-symbol `type` modifiers, and checks each runtime symbol against the installed pi.
  Result after the fix: **0 missing** across `pi-agent-core` (0 used), `pi-coding-agent`,
  `pi-ai` and `pi-tui`. Hot-path `pi-ai` runtime imports
  (`createAssistantMessageEventStream`, `getCurrentTools`, `getCurrentSystemPrompt`,
  `calculateCost`) all resolve.

## Remaining risk

- `provider-manager/__tests__/message-utils.test.ts` imports
  `../../../github特供版/github-dist/provider-manager/lib/message-utils.js`, which does not
  exist in this checkout. That test file cannot run here; pre-existing, unrelated to this fix.
- The repo still pins `@earendil-works/*` `0.87.1` in `node_modules` while the installed pi is
  `1.1.0`. Future symbols moved in 1.1.x will keep compiling and failing at runtime. Re-run
  `temp/audit-runtime-symbols.mjs` after every pi upgrade; it is the cheap early-warning.
